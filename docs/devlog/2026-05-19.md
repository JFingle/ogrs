## Detail per item

### Run-energy (#9, commit A — server-side mechanic)

`want_run_energy: true` in `ogrs.conf`. New per-player state on `Player.java`:

```
MAX_RUN_ENERGY       = 10000     (0..100% display = 0..10000 internal)
RUN_DRAIN_PER_TILE   = 100       (100 tiles per full bar)
RUN_REGEN_IDLE       = 80        (~80s idle to refill from empty)
RUN_REGEN_WALKING    = 40        (~160s walking to refill)
```

`WalkingQueue.processNextMovement()` was refactored. Now:

1. Takes one tile via the new `takeOneStep()` helper.
2. If the mob is a running player with energy > 0, drains
   `RUN_DRAIN_PER_TILE` and takes a second tile (drains again).
3. If just walking, regens at the walking rate.
4. If idle this tick, regens at the idle rate.

Adjacency check still fires per step → pathfinding stays sane.

Toggle is transient (resets to false on each login). Energy itself **does
not persist** to DB yet — you start every login at 100% energy. That's
fine for v1; persistence is queued as **#37 Run-energy Commit B** along
with the minimap UI + wire-format packet.

Commands (in `plugins/custom/commands/RunEnergyCommand.java`):
- `::run` / `::running` / `::sprint` — toggle running
- `::energy` — print current energy

### Firemaking: tinderbox + log in inventory (#23)

`Firemaking.java#onUseInv` used to message "I think you should put the
logs down before you light them!" and do nothing. Now it:

1. Identifies which item is the tinderbox vs the log.
2. Validates the tile is fire-able.
3. Removes one log from inventory.
4. Spawns it as a GroundItem under the player (`registerItem` with
   `GAME_TICK * 145` lifetime, same pattern as full-inventory gp drops).
5. Re-invokes the existing `onUseObj` firemaking path with the
   freshly-dropped log so all formula/XP/batch logic stays in one place.

Same behavior whether you use-on or right-click "Use" with the inventory
pair.

Also fixed in `08c2929`: `Inventory.remove()` returns `long` (slot
removed or -1 on failure), not `boolean`. First attempt at the change
applied `!` to a long which doesn't compile. Now checks `< 0`.

### Codegen-client-items: wieldable + wearable_id support

Commit `69c01ba`. Quality-of-life extension to
`tools/codegen-client-items.py` — the generated `ItemDef` constructor
call previously hardcoded `false, 0` for the wieldable and wearableID
fields, so the YAML pipeline couldn't ship a weapon or armour piece.
Now those fields are read from YAML:

```yaml
wieldable: true
wearable_id: 49
```

Existing item YAMLs are unaffected — defaults preserve the old
no-op behavior. **Server-side weapon STATS (aim/power/required-skill/
wieldPosition) still need to live in ItemDefsCustom.json** until a
follow-up extends the YAML loader to carry those too.

### Slayer -bane gear (#36) — rolled back

Started, got halfway, then rolled back. The proper-fit architecture
turned out to be bigger than the quick-win bucket:

The YAML pipeline only knows about display-side ItemDef fields. Weapon
stats (aim/power/wieldPosition/requiredLevel/requiredSkillID) live
exclusively in ItemDefsCustom.json on the server side. Server's
`OgrsContentItemLoader.requireSequentialAfter()` enforces that YAML ids
can't overlap with JSON ids, so I can't double-define the same id in
both pipelines to get JSON-side weapon stats + YAML-side client display.

Three workable architecture choices captured in task #36's notes:

  - **A**: Extend YAML schema + server loader + codegen so weapon items
    ship end-to-end through YAML. ~2-3 hour focused effort.
    Aligned with project's data-driven philosophy.
  - **B**: JSON-only items, teach YAML loader to SKIP already-defined
    ids. Needs Cache binary surgery for client to know the item.
  - **C**: Separate `codegen-client-weapons.py` pipeline. Most code,
    cleanest separation.

Path A is the recommendation. Existing sketch (rollbacked) had:
  - `OgrsSlayerBane.java` content helper with per-weapon bane mapping
  - `CombatFormula.doMeleeDamage` hook applying the multiplier
  - Iron Dagger of Spiderbane as the first item (req: Slayer 1, +5% vs
    every spider variant id we know about)

That work is recoverable from git reflog if needed when we pick this up
properly.

### Run-energy Commit B (MVP) — `70d222c`

Clickable **RUN: ON / RUN: OFF** button rendered in the minimap tab,
just below the minimap proper at (posX+4, posY+156). 70x18 px, same
red-when-active styling as the bank UI quantity buttons.

Pragmatic implementation that ships in one client-only commit instead
of the multi-file protocol surgery the originally-planned packet pair
needed:

  - Click calls `sendCommandString("run")` — the SAME outgoing packet
    (opcode 38) that fires when the player types `::run` in chat.
  - Server's `RunEnergyCommand` plugin handles it identically to chat
    invocation: flips state, echoes "Running: ON — Energy: 87%" via
    the chat system.
  - Local field `ogrsRunButtonVisual` tracks click-time state for the
    button's red/grey color. Can desync if the server force-disables
    running (energy 0) — caveat documented at the field declaration.

The proper Commit C (SEND_RUN_ENERGY packet pushing live state + 60x4
energy bar above the button + dedicated TOGGLE_RUN incoming packet
replacing the chat-command route) is queued as #37 with the full spec.
~1-2 hour focused session when we get there; touches ~10 per-protocol
payload generators.

Why minimap tab specifically: it's the "navigation" UI surface where
players who want to run are already going. The button render is gated
on showUiTab == MINIMAP_AND_COMPASS_TAB so it doesn't leak into other
tabs.
